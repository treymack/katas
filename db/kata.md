# DB Kata: Persisting the Music Vault

Wire up a real database to the Music Vault domain. The domain model is defined in the REST API kata — this kata is about everything below the API layer: schema design, migrations, and the quirks of your chosen database engine and ORM.

**Stack:** .NET. Choose your ORM and database engine at kata time (see Design Decisions).

---

## Goal

Replace an in-memory store with a real database. At minimum, all five domain entities must be persisted with their relationships intact:

- `Instrument`
- `Musician`
- `Band`
- `Membership` (musician ↔ band, temporal)
- `InstrumentAssociation` (musician ↔ instrument)

If you have a working REST API from the previous kata, wire this into it. If not, a working data layer with migrations and a seed script is sufficient.

---

## Design Decisions

Make each of these choices explicitly before writing code.

### 1. ORM

| | EF Core | Dapper + DbUp |
|---|---|---|
| Style | Full ORM — change tracking, LINQ queries, code-first migrations | Micro-ORM — raw SQL queries, script-based migrations |
| Control | Convention-driven; EF generates SQL for you | You write every query and every migration script |
| Good for | Learning ORM patterns, entity configuration, LINQ | Learning actual SQL, understanding what's hitting the database |
| Migration tool | `dotnet ef migrations add` | DbUp runs numbered `.sql` script files in order |

Pick one. Note what drove the decision.

### 2. Database Engine

| | SQLite | SQL Server |
|---|---|---|
| Setup | Zero — file on disk | Local instance, LocalDB, or Docker |
| Good for | Speed, simplicity, offline | Production parity, full SQL feature set |
| Quirks | Limited `ALTER TABLE` in migrations; no native UUID column type; case-insensitive strings by default | Requires a running server; stricter types and nullability |
| EF Core provider | `Microsoft.EntityFrameworkCore.Sqlite` | `Microsoft.EntityFrameworkCore.SqlServer` |
| Dapper | `Microsoft.Data.Sqlite` | `Microsoft.Data.SqlClient` |

Pick one. Then consider: what would you have to change to swap engines later?

### 3. Primary Keys

UUIDs are used in the REST API domain. Decide who generates them and how they're stored:

- Generated by the app (`Guid.NewGuid()` before insert) — ID is known immediately, no round-trip needed
- Generated by the database (`newid()` / `gen_random_uuid()`) — ID unknown until after insert
- Sequential GUID (`RT.Comb` or SQL Server's `newsequentialid()`) — reduces index fragmentation

### 4. Instrument Type Enum

`Instrument.type` is an enum in the domain. Decide how to store it:

- As an `int` (compact, but opaque in raw SQL queries)
- As a `string` (readable, protects against reordering the enum)

### 5. Entity Configuration *(EF Core only)*

**Data annotations** (`[Required]`, `[MaxLength]`, `[Column]`) live on the model class — convenient but mixes persistence concerns into the domain.

**Fluent API** (`.HasRequired()`, `.HasMaxLength()`, `.HasColumnName()`) lives in `OnModelCreating` or separate `IEntityTypeConfiguration<T>` classes — more verbose but keeps models clean.

Pick one and use it consistently.

### 6. Nullable Reference Types *(EF Core only)*

EF Core 6+ infers column nullability from C# nullable reference type annotations. Decide whether to enable NRTs and let EF infer, or configure nullability explicitly via Fluent API.

## Requirements

### Schema

All five entities must be represented with correct column types, nullability, and constraints:

- Primary keys on all tables.
- Foreign key constraints enforced at the database level.
- `Instrument.type` stored using your chosen enum strategy.
- `Membership` has a composite natural key of `(musicianId, bandId, since)` — a musician can have multiple tenures in the same band.
- `InstrumentAssociation` has a composite primary key of `(musicianId, instrumentId)`.

### Migrations

**EF Core path:**

- Generate migrations with the EF CLI (`dotnet ef migrations add`), not by hand.
- `dotnet ef database update` on a clean database must produce a working schema.
- Include at least one follow-up migration that alters the schema (e.g., add an index, add a column).

**Dapper + DbUp path:**

- Write SQL migration scripts by hand, numbered sequentially (e.g., `0001_initial_schema.sql`, `0002_add_index.sql`).
- DbUp tracks which scripts have run in a journal table — `dotnet run` on a clean database must apply all scripts in order.
- Include at least two scripts to practice the incremental migration workflow.

### Seed Data

Write a seed script that populates:

- At least 3 musicians
- At least 2 bands
- At least 3 instruments (at least one with a famous name)
- At least one musician in two different bands
- At least one instrument associated with two different musicians

EF Core: use `HasData` in `OnModelCreating` or a startup seeder. Dapper + DbUp: a dedicated seed script or a seeder class using `IDbConnection`.

Real data is more interesting — use actual bands and musicians.

### Queries

Demonstrate that the schema works by implementing (or testing) these queries without loading entire tables into memory:

1. All current members of a given band (membership where `until` is null).
2. All instruments associated with a given musician, flagging which is primary.
3. All bands a musician has ever been in, ordered by `since`.
4. All named instruments (`name` is not null).

## Rules

**All paths:**

- Connection strings must come from configuration (`appsettings.json` or environment variables), not be hardcoded.
- All queries must be parameterized — no string concatenation with user-supplied values.

**EF Core:**

- Use explicit `.Include()` / `.ThenInclude()` where needed. Lazy loading is off.
- The `DbContext` must not be a singleton — register it with the correct lifetime.

**Dapper + DbUp:**

- Write queries as explicit SQL — no query building via string concatenation.
- Keep connection management consistent: open, use, dispose. Don't leak connections.

## Stretch Goals

1. **Repository pattern** — Introduce a repository abstraction over your data layer. Then ask: does it actually add value here, or is it just wrapping the ORM for no reason? Write down your conclusion.

2. **Optimistic concurrency** — Add a `rowVersion` concurrency token to `Band` or `Musician`. EF Core handles this with `[Timestamp]`; Dapper requires you to check the token manually in your UPDATE and handle the conflict yourself.

3. **Temporal tables** *(SQL Server only)* — Convert `Membership` to a system-versioned temporal table. Query the history. Consider: does this replace the `since`/`until` columns, or complement them?

4. **Engine swap** — Switch from SQLite to SQL Server or vice versa. Document every change required. This is the real test of whether your abstraction held up.

5. **Connection resiliency** — Handle transient failures. EF Core has a built-in retry strategy; Dapper needs Polly or equivalent. Understand when retry applies and when it doesn't (hint: not inside explicit transactions).
